IAES Specification v1.3

Complete technical reference for the Industrial Asset Event Standard.

March 2026

1. Purpose

IAES defines how industrial asset signals, diagnoses, and maintenance intents are represented and transferred across heterogeneous operational systems.

IAES is not a product. It is a data contract. Any system — sensor platform, AI engine, CMMS, historian, or dashboard — can produce or consume IAES events without knowing the implementation details of the other side.

2. Principles

  1. Vendor neutrality — No dependency on SAP, PI System, Odoo, or any specific vendor.
  2. Legacy compatibility — Events map cleanly to CMMS, historians, SCADA, and IoT platforms.
  3. Event-oriented — Each object represents something that happened (measurement, diagnosis, intent).
  4. Complete traceability — Every event traces back to its origin via event_id, correlation_id, source_event_id.
  5. Extensibility — The data payload and metadata field allow new fields without breaking consumers.

3. Terminology

Term Definition
EventA single occurrence: a measurement, a diagnosis, a maintenance intent, or a completion report.
ProducerAny system that creates IAES events (sensor platforms, AI engines, manual entry tools).
ConsumerAny system that receives and acts on IAES events (CMMS, dashboards, historians, ERPs).
EnvelopeThe common wrapper that every IAES event shares: spec_version, event_type, event_id, timestamps, asset identity, and the data payload.
CorrelationA shared correlation_id that links related events across the lifecycle (measurement → health → work order → completion).
SourceThe source field identifying the originating system in dot-notation: vendor.system.subsystem.
IntentA maintenance.work_order_intent event that recommends a maintenance action. It is not a work order — the consumer decides whether to create one.
Health IndexA normalized 0.0 – 1.0 score representing the overall health of an asset (1.0 = perfect, 0.0 = failed).
RULRemaining Useful Life. An estimate of how many days an asset can continue operating before failure.

4. Common Envelope

Every IAES event is wrapped in a common envelope. The envelope carries identity, traceability, and routing information. The event-specific payload lives inside the data field.

JSON — Common Envelope
{
  "spec_version": "1.3",
  "event_type": "asset.health",
  "event_id": "uuid",
  "correlation_id": "uuid",
  "source_event_id": "uuid | null",
  "batch_id": "string | null",
  "timestamp": "ISO 8601",
  "source": "vendor.system.subsystem",
  "content_hash": "sha256_16char",
  "asset": {
    "asset_id": "string",
    "asset_name": "string | null",
    "plant": "string | null",
    "area": "string | null"
  },
  "data": {}
}

Field Definitions

Field Type Required Description
spec_version string Yes IAES specification version. Currently "1.3".
event_type string Yes One of the 7 defined event types (e.g. asset.measurement, asset.health).
event_id string (UUID v4) Yes Unique identifier for this event. Generated by the producer.
correlation_id string (UUID v4) Yes Shared identifier that links related events in a chain (measurement → health → work order → completion).
source_event_id string | null No The event_id of the event that directly triggered this one. Null for the first event in a chain.
batch_id string | null No Optional identifier for grouping events that were produced together (e.g. a batch of measurements from one collection run).
timestamp string (ISO 8601) Yes When the event occurred. Must include timezone (preferably UTC). Example: 2026-03-08T14:32:00Z.
source string Yes Dot-notation identifier of the producing system: vendor.system.subsystem. Example: wertek.vibration.ai_engine.
content_hash string Yes First 16 characters of the SHA-256 hash of the canonical JSON data payload. Used for deduplication.
asset object Yes Asset identity block. Must contain at least asset_id.
data object Yes Event-specific payload. Structure depends on event_type.

Asset Identity

The asset block identifies the target asset. Only asset_id is required; the remaining fields provide human-readable context and hierarchical location.

JSON — Asset Identity
{
  "asset": {
    "asset_id": "PUMP-001",
    "asset_name": "Main Cooling Water Pump",
    "plant": "Plant A - Monterrey",
    "area": "Cooling Tower Area"
  }
}

5. Event Types

IAES v1.3 defines 7 event types organized into 3 domains: asset signals, maintenance actions, and sensor lifecycle.

asset.measurement v1.0

A single measurement reading from an asset. This is the most fundamental event type — it captures raw sensor data from vibration, temperature, current, pressure, or any other measurable quantity.

Field Type Required Description
measurement_type string Yes Type of measurement (e.g. vibration_velocity, temperature, current_rms, pressure).
value number Yes The measured value.
unit string Yes Unit of measurement (e.g. mm/s, °C, A, bar).
sensor_id string No Identifier of the sensor that took the measurement.
location string No Measurement location on the asset (e.g. bearing_drive_end, motor_frame).
units_qualifier string No Qualifier for the unit value (e.g. rms, peak, peak_to_peak). v1.2
sampling_rate_hz number No Sampling rate in Hz used for the acquisition. v1.2
acquisition_duration_s number No Duration of the acquisition window in seconds. v1.2

asset.health v1.0

A health assessment for an asset. Produced by AI engines, rule-based systems, or human experts. Links to the measurement(s) that triggered it via source_event_id and correlation_id.

maintenance.work_order_intent v1.0

A recommendation to create a maintenance work order. This is an intent, not a work order itself. The receiving CMMS decides whether to accept, modify, or reject it. This decoupling is fundamental to IAES — the AI or rule engine recommends, the CMMS decides.

Field Type Required Description
title string Yes Short title for the work order.
description string No Detailed description of the issue and recommended action.
priority string Yes One of: low, medium, high, emergency.
recommended_due_days number No Suggested deadline in days from now.
triggered_by string No What triggered this intent (e.g. ai_diagnosis, threshold_rule, manual).
Severity vs. Priority: severity (in asset.health) describes the condition of the asset. priority (in work_order_intent) describes the urgency of the maintenance action. A high severity issue on a non-critical pump might only warrant a medium priority work order if a backup pump is available.

6. Severity Levels

IAES defines 5 severity levels used in asset.health events. These represent the condition of the asset, not the urgency of the maintenance response.

Severity Health Index Range Meaning
info 0.90 – 1.00 Normal operating condition. No action needed.
low 0.70 – 0.89 Minor deviation detected. Monitor and schedule inspection during next planned downtime.
medium 0.50 – 0.69 Moderate degradation. Plan corrective action within weeks.
high 0.25 – 0.49 Significant degradation. Schedule maintenance within days.
critical 0.00 – 0.24 Imminent failure or failed. Immediate action required.

7. Idempotency

IAES provides three mechanisms for deduplication and idempotent processing:

  1. event_id — Every event has a globally unique UUID. Consumers must track processed event IDs to avoid reprocessing.
  2. content_hash — A deterministic hash of the data payload. Two events with the same content_hash for the same asset and event type are semantically identical.
  3. correlation_id — Links related events. If a consumer already has a work order for a given correlation_id, it should not create a duplicate.

content_hash Computation

The content_hash is computed as follows:

  1. Serialize the data object as canonical JSON (keys sorted alphabetically, no whitespace).
  2. Compute the SHA-256 hash of the resulting string.
  3. Take the first 16 hexadecimal characters.
Deduplication rule: An event is a duplicate if an existing event shares the same content_hash + asset.asset_id + event_type combination.

8. Producer Guidelines

Required

  1. Generate a unique event_id (UUID v4) for every event.
  2. Set spec_version to "1.3" (or the version you implement).
  3. Compute and include a valid content_hash for every event.
  4. Use ISO 8601 timestamps with timezone information (UTC preferred).
  5. Include all required fields for the chosen event_type.

Recommended

  1. Set correlation_id = event_id for the first event in a chain; propagate the same correlation_id for subsequent linked events.
  2. Set source_event_id to the event_id of the directly upstream event.
  3. Use the dot-notation format for source: vendor.system.subsystem.
  4. Use failure modes from Appendix A when applicable.
  5. Include ISO 14224 and ISO 13374 fields when the data is available to maximize interoperability.

9. Consumer Guidelines

Required

  1. Validate spec_version and reject events from unsupported versions.
  2. Implement deduplication using event_id or content_hash (see Section 7).
  3. Ignore unknown fields in data without raising errors (forward compatibility).

Recommended

  1. Use correlation_id to group related events for display and analytics.
  2. Map IAES severity to your system's native priority/urgency model.
  3. Store the full IAES event as an audit record, even after mapping to native format.
  4. Implement retry logic with exponential backoff for transient processing failures.
  5. Log rejected or malformed events for troubleshooting.

10. Typical Flow

A typical IAES event chain follows this pattern. All events in the chain share the same correlation_id, and each event references its direct predecessor via source_event_id.

asset.measurement Sensor data collected
→
asset.health AI diagnosis
→
work_order_intent Maintenance recommended
→
completion Work executed
→
spare_part_usage Parts consumed
Correlation Chain
// All events share the same correlation_id
correlation_id: "a1b2c3d4-e5f6-4a7b-8c9d-0e1f2a3b4c5d"

// Event chain via source_event_id:
measurement  (event_id: AAA, source_event_id: null)
    ↓
health       (event_id: BBB, source_event_id: AAA)
    ↓
wo_intent    (event_id: CCC, source_event_id: BBB)
    ↓
completion   (event_id: DDD, source_event_id: CCC)
    ↓
spare_part   (event_id: EEE, source_event_id: DDD)

Appendix B: ISO 14224 Codes

The iso_14224 object provides standardized failure classification per ISO 14224:2016 (Petroleum, petrochemical and natural gas industries — Collection and exchange of reliability and maintenance data). This object can appear in asset.health and maintenance.completion events.

iso_14224 Object Structure

JSON — iso_14224 object
{

Appendix C: ISO 13374 Mapping

ISO 13374 (Condition monitoring and diagnostics of machines) defines a 6-block processing model for condition monitoring. IAES maps naturally to this standard. The iso_13374_status field in asset.health events provides explicit alignment.

iso_13374_status Levels

iso_13374_status Description Nearest IAES Severity
normal Operating within acceptable parameters info
satisfactory Minor deviations, within limits low
unsatisfactory Outside normal limits, monitoring required medium
unacceptable Exceeds limits, corrective action needed high
imminent_failure Failure expected imminently critical
failed Equipment has failed critical

ISO 13374 Processing Model → IAES Events

ISO 13374 Block Function IAES Event
Block 1: Data Acquisition Sensor data collection sensor.registration
Block 2: Data Manipulation Signal processing, filtering asset.measurement
Block 3: State Detection Threshold comparison, anomaly detection asset.health (health_index, anomaly_score)
Block 4: Health Assessment Diagnosis, severity, failure mode asset.health (severity, failure_mode, rul_days)
Block 5: Prognostics RUL estimation, trend prediction asset.health (rul_days, recommended_action)
Block 6: Advisory Generation Recommended actions, work orders maintenance.work_order_intent
