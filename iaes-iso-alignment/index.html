IAES ISO Alignment

Field-level mapping to ISO 55000, 13374, 17359, and 14224

The Industrial Asset Event Standard (IAES) was designed from the ground up with ISO alignment in mind. Rather than inventing proprietary concepts, IAES maps its event types and fields directly to four foundational ISO standards that govern asset management, condition monitoring, measurement practices, and failure classification in industrial environments.

This page provides a field-level mapping between IAES v1.2+ and each ISO standard. Whether you are building a condition monitoring system, integrating with a CMMS, or establishing an ISO 55001-compliant asset management program, this reference shows exactly how IAES events carry the data each standard requires.

All ISO-related fields in IAES are optional and backward-compatible. Systems that do not need ISO compliance can ignore these fields entirely. Systems that do need it get standards-aligned data without custom transformation layers.

ISO 55000 — Asset Management Fundamentals

How IAES implements the four pillars of asset management defined by ISO 55000.

ISO 55000 defines four fundamental concepts that every asset management system must embody: Value, Alignment, Leadership, and Assurance. These are not specific data fields or technical requirements — they are organizational principles. IAES implements each one through its 7 event types and the relationships between them.

Value

Assets exist to deliver value. IAES makes value measurable: asset.measurement captures quantified condition data tied to specific assets. asset.health produces value-weighted health scores. Every event carries an asset_id — the asset is the organizing principle, not the sensor, not the system. This asset-centric model means you can always answer: "What is the current state and value contribution of this asset?"

Alignment

Maintenance decisions must align with organizational objectives. maintenance.work_order_intent translates condition data into prioritized actions. The priority field maps organizational risk tolerance directly into the event stream. A "critical" priority on a cooling pump in a power plant means something different than "critical" on a warehouse fan — the priority reflects organizational context, not just sensor thresholds.

Leadership

ISO 55000 requires clear accountability and traceability. IAES provides this through the correlation_id field, which links every event in an incident chain — from the first anomalous measurement through health assessment, work order creation, and completion. This creates a complete decision audit trail: who detected what, when was action recommended, and who executed it.

Assurance

Assurance means closing the loop: did the maintenance action actually resolve the problem? maintenance.completion with its failure_confirmed field answers this directly. When the AI predicted bearing wear and the technician confirmed bearing wear during replacement, that is a verified feedback loop. When the prediction was wrong, the correction feeds back into model improvement. IAES makes assurance auditable by design.

ISO 13374 — Condition Monitoring 6-Block Model

IAES maps directly to each block of the ISO 13374 processing pipeline.

ISO 13374 defines a 6-block processing pipeline that transforms raw sensor data into actionable maintenance decisions. This model is the backbone of every condition monitoring system. IAES does not replace the processing within each block — it standardizes the data that flows between blocks, making every stage interoperable.

ISO 13374 Block Function IAES Event Type IAES Field
Block 1: Data Acquisition (DA) Sensor sampling asset.measurement sampling_rate_hz, acquisition_duration_s
Block 2: Data Manipulation (DM) Signal processing asset.measurement units_qualifier (rms, peak, peak_to_peak)
Block 3: State Detection (SD) Threshold comparison asset.health iso_13374_status
Block 4: Health Assessment (HA) Severity classification asset.health health_index (0–1), severity
Block 5: Prognostic Assessment (PA) Remaining useful life estimation asset.health rul_days
Block 6: Advisory Generation (AG) Action recommendation maintenance.work_order_intent title, priority, description

The iso_13374_status field in asset.health events uses values that map directly to ISO 13374 condition states. These represent a progression from normal operation to confirmed failure:

Status Value Meaning Typical Action
normal Operating within acceptable parameters Continue monitoring
satisfactory Minor deviation, no action needed Increase monitoring frequency
unsatisfactory Deviation requires planned intervention Schedule maintenance
unacceptable Significant deviation, urgent intervention Priority work order
imminent_failure Failure expected imminently Emergency shutdown / immediate repair
failed Asset has failed Corrective maintenance

ISO 17359 — Condition Monitoring & Diagnostics

Three fields added in IAES v1.2 for ISO 17359 measurement compliance.

ISO 17359 defines how vibration, temperature, and other condition monitoring measurements should be recorded for diagnostic purposes. A vibration reading of "4.5 mm/s" is ambiguous without context: is it RMS or peak? What was the sampling rate? How long was the measurement window? These details matter for accurate diagnosis and trending.

IAES v1.2 added three optional fields to asset.measurement that resolve these ambiguities:

units_qualifier

Resolves the most common ambiguity in vibration measurements. When you see "4.5 mm/s", is that RMS or peak? The qualifier makes it explicit. Accepted values: rms, peak, peak_to_peak, average, true_rms. This field applies to any measurement type, not just vibration — temperature, current, pressure all benefit from explicit qualification.

sampling_rate_hz

Sample rate in Hz. Critical for vibration analysis due to the Nyquist theorem: to detect a 10 kHz bearing defect frequency, you need at least 20 kHz sampling. Recording the sampling rate means downstream systems can validate whether the measurement is trustworthy for a given analysis. Example: 25600 Hz for high-frequency bearing detection.

acquisition_duration_s

Duration of the measurement window in seconds. A 0.1-second capture misses low-frequency phenomena. A 10-second capture provides better frequency resolution but larger data. Recording this value enables apples-to-apples trending: you can only compare measurements taken with the same acquisition parameters. Example: 2.0 seconds for standard vibration capture.

Here is an asset.measurement event with all three ISO 17359 fields populated:

// asset.measurement with ISO 17359 fields { "event_type": "asset.measurement", "asset": { "asset_id": "FAN-2201" }, "data": { "measurement_type": "vibration", "value": 4.5, "unit": "mm/s", "units_qualifier": "rms", "sampling_rate_hz": 25600, "acquisition_duration_s": 2.0 } }

ISO 17359 also defines a 4-zone alarm system (Zones A through D) for classifying machine vibration severity. IAES maps these zones through the severity field on asset.health events:

ISO 17359 Zone Meaning IAES severity
Zone A — Good Newly commissioned or excellent condition info
Zone B — Acceptable Long-term operation acceptable low
Zone C — Alert Not suitable for sustained operation medium / high
Zone D — Danger Risk of damage, shutdown recommended critical

ISO 14224 — Failure Classification

Standardized failure codes for reliability data collection, embedded directly in IAES events.

ISO 14224 defines standardized codes for recording what failed, why it failed, and how the failure was detected. This data is essential for reliability engineering: calculating MTBF, identifying systemic failure patterns, and justifying capital investment in predictive maintenance. Without standardized codes, failure data across plants and systems cannot be compared or aggregated.

IAES v1.2 added an optional iso_14224 object to both asset.health and maintenance.completion events. This creates a powerful feedback loop: the AI system predicts a failure mode, and the technician confirms or corrects it after repair.

// iso_14224 object in asset.health or maintenance.completion { "iso_14224": { "mechanism_code": "BRG", "mechanism_label": "Bearing failure", "cause_code": "LUB", "cause_label": "Lubrication failure", "detection_method": "VIB", "detection_label": "Vibration monitoring" } }

The feedback loop works like this: An AI engine analyzes vibration data and emits an asset.health event with iso_14224.mechanism_code: "BRG" (bearing failure predicted). A work order is created. The technician replaces the bearing and closes the work order. The bridge emits a maintenance.completion event — if the technician confirmed bearing wear, the same BRG code appears. If the actual root cause was misalignment, the technician corrects it to ALN. Both events share a correlation_id, so the ML model can learn from the correction.

Failure Mode Taxonomy (IAES Appendix A): IAES defines standard failure_mode values based on ISO 14224, organized by equipment category:

Rotating Equipment

  • bearing_inner_race
  • bearing_outer_race
  • misalignment
  • unbalance
  • looseness_mechanical
  • gear_mesh

Electrical

  • electrical_fault
  • winding_short
  • broken_rotor_bar
  • eccentricity

Fluid / Thermal

  • cavitation
  • overheating
  • lubrication_failure
  • seal_leak
  • fouling
  • corrosion

Master Mapping Table

Complete ISO-to-IAES alignment at a glance.

ISO Standard Focus IAES Event Types Key IAES Fields
ISO 55000 Asset management fundamentals All 7 event types correlation_id, asset_id
ISO 13374 Condition monitoring pipeline asset.measurement → asset.health → work_order_intent iso_13374_status, health_index
ISO 17359 Measurement standards asset.measurement units_qualifier, sampling_rate_hz, acquisition_duration_s

Together, these four standards cover the full lifecycle of industrial asset management: ISO 55000 provides the strategic framework, ISO 13374 defines the condition monitoring pipeline, ISO 17359 ensures measurement quality, and ISO 14224 standardizes failure data for reliability analysis. IAES carries all of this in a single, lightweight JSON event format — no separate data models, no transformation layers, no proprietary extensions.

All ISO-related fields are part of the IAES v1.2 specification and are validated by the published JSON schemas. The Python SDK (pip install iaes) and TypeScript SDK (npm install @iaes/sdk) both support ISO field validation out of the box.
